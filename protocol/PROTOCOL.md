# SmartConnectLike — Local Protocol (v1)

Everything runs on the local network (Wi‑Fi / hotspot). No cloud, no accounts.

## 1. Discovery (UDP)

| Item | Value |
|---|---|
| Port | `47777` |
| Transport | UDP broadcast (`255.255.255.255` + per-interface broadcast) |
| Interval | every 2000 ms, peer expires after 8000 ms |

Packet (UTF‑8 JSON, one datagram):

```json
{
  "sc": "hello",
  "v": 1,
  "id": "c0ffee00-1234-4abc-9def-0123456789ab",
  "name": "MARWA-PC",
  "kind": "desktop",           // "desktop" | "tablet"
  "ws": 47800,                  // signaling / control WebSocket port
  "http": 47801,                // file transfer HTTP port
  "features": ["mirror", "extend", "files", "input", "clipboard"]
}
```

Both sides answer a `hello` with their own `hello` (unicast to the sender).

## 2. Signaling WebSocket

`ws://<peer-ip>:47800/ws`

The **desktop** always runs the WebSocket server. The tablet connects to it as a client.
Messages are JSON objects with a `type` field.

| type | direction | payload |
|---|---|---|
| `hello` | both | `deviceId`, `deviceName`, `kind` |
| `ping` / `pong` | both | `t` (timestamp) |
| `open-viewer` | desktop → tablet | `mode` (`mirror-pc`, `extend`) — asks the tablet to open its fullscreen viewer |
| `session-request` | tablet → desktop | `session`, `mode` (`mirror-pc`, `extend`, `mirror-tablet`) |
| `session-accept` | desktop → tablet | `session`, `mode` |
| `session-stop` | both | `session` |
| `signal` | both | `session`, `data: { kind: "offer" \| "answer" \| "ice", sdp?, candidate? }` |
| `input` | tablet → desktop | `session`, `event: { t: "move"\|"down"\|"up"\|"scroll"\|"key"\|"tap", x, y (0..1), button?, dy?, key? }` |
| `clipboard` | both | `text` |
| `toast` | both | `level`, `text` |

Session ids are UUIDs generated by the side that opens the session.
Signaling is forwarded verbatim to the renderer / Android WebRTC layer.

### PC-initiated sessions (`open-viewer` handshake)

The tablet only receives video while its fullscreen viewer (`MirrorActivity`) is open, so
the desktop never streams blindly:

1. Desktop: user presses **Show on tablet** → desktop remembers the chosen capture target
   and sends `{ "type": "open-viewer", "mode": "extend" | "mirror-pc" }`.
2. Tablet: `MainActivity` opens `MirrorActivity` with that mode (`singleTop`, so an already
   open viewer is reused via `onNewIntent`).
3. Tablet: viewer sends `session-request` with the same `mode` and a fresh `session` id.
4. Desktop: consumes the remembered target (whole desktop, one monitor, or one window), calls
   `getDisplayMedia`, and sends the WebRTC offer.

If no `session-request` arrives within 15 s, the desktop shows
"tablet ne viewer nahi khola" and sends nothing.

## 3. File transfer (HTTP)

Desktop server: `http://<ip>:47801`

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/info` | `{ name, kind, version, os }` |
| `GET` | `/api/files` | list of files shared from the desktop |
| `GET` | `/api/file/<token>` | download a shared file (`Content-Disposition`) |
| `POST` | `/api/upload?name=<urlencoded>` | tablet → desktop upload; desktop saves into the receive folder |
| `POST` | `/api/share` | desktop UI → register a local path as shareable, returns token |

Responses are plain JSON except file bodies. `Content-Length` is always set so both
sides can show a progress bar.

## 4. WebRTC

* Host candidates only (LAN). No STUN/TURN required.
* `mirror-tablet`: tablet captures its screen (MediaProjection) and offers; desktop renders.
* `mirror-pc`: desktop captures the selected screen/window and offers; tablet renders.
* `extend`: desktop captures one chosen monitor (by `displayId`) or one chosen app window and
  offers; tablet renders it fullscreen and forwards normalized touch points (`0..1`), which the
  desktop maps onto that monitor's physical pixel rect (or the window rect). Virtual monitors
  come from a signed display driver such as MTT Virtual Display Driver — see README; without one
  only the primary mirror and single-window targets exist.
* Video: 1280x720 @ 30 fps, 2.5 Mbps start, VP8/H264 negotiated.
* Control channel: `input` messages from the tablet are mapped onto the host cursor.
